基于对项目代码的完整梳理（并结合几次实际运行踩过的坑），我把优化建议按**优先级 + 投入产出比**分成四档。已确认过几个关键事实：`validate()` 和 token 预算是死代码、流式调用不统计 token、logger 无 handler、无中断机制。

## P0 级：隐患修复（强烈建议先做）

**1. token 预算目前是"空头支票"**
`settings.py` 里的 `round_token_budget=8000`、`total_token_budget=50000` 定义了但**零处使用**。目前唯一的成本闸门是 `max_rounds`，如果某轮 Generator 生成了超长内容、或连续重试，成本会失控。
→ 方向：在 `Orchestrator.run()` 循环里，每轮/累计检查 `total_tokens_used`，超预算即提前终止。

**2. 流式调用不统计 token**
`base.py` 里只有 `call_llm`（`invoke`）累计 `total_tokens_used`，`call_llm_stream`（Web 正在用的路径）完全不累计。意味着 Web 模式下你看到的 token 统计是 0。
→ 方向：从 `stream` 的每个 chunk 读取 `usage_metadata`（通常在最后一个 chunk）补上统计。

**3. 缺少真正的中断机制**
Web 的"停止接收"按钮只是 `es.close()` 断开 SSE，**后台线程仍会跑完当前整轮迭代**（一轮里 Generator+Critic 各一次调用，可能要几十秒）。
→ 方向：给 Orchestrator 加一个 `threading.Event` 停止标志，每轮循环开始时检查，SSE 断开时置位。

**4. 重试策略过于粗放**
`call_llm_with_retry` 对**所有异常**都重试。但 `401`（key 错）、`400`（参数错）这类错误重试 3 次毫无意义，反而拖慢失败反馈。
→ 方向：区分"可重试"（超时、429 限流、5xx）和"不可重试"（401/400）错误，后者直接抛。

## P1 级：工程健壮性

**5. 收敛逻辑有两份重复实现**
`orchestrator.py` 和 `graph/workflow.py` 各写了一遍收敛判断，且条件顺序、细节已有轻微不一致（比如 graph 版把"最大轮数"判断放在了"无新反馈"之前）。改一处容易漏另一处。
→ 方向：抽取一个纯函数 `check_convergence(state, ...)` 供两处共用。

**6. `validate()` 是死代码**
`SystemConfig.validate()` 定义完整（检查 key 缺失、轮数/阈值合法性），但 `get_config()` 和 `reload_config()` 都没调用它。配错参数不会立刻报错，而是跑到一半才崩。
→ 方向：在 `get_config()` 里返回前调用一次 `validate()`。

**7. logger 未配置 handler**
所有模块都用 `logging.getLogger(__name__)`，但没有任何 `basicConfig` 配置，导致 `logger.info` 在控制台静默（这也是之前"终端运行看不到内容"的间接原因之一）。
→ 方向：在入口统一配置一次日志级别/格式（`DEBUG` 环境变量目前也没接上）。

## P2 级：能力增强（产品价值提升）

**8. Generator 缺少"全局记忆"**
现在每轮只给 Generator「上一版 draft + 上一轮 critique」，它看不到前几轮改了什么、被否定过什么，容易**重复犯同样的错或来回横跳**。
→ 方向：把 `state.history` 的历史 critique 摘要（尤其是"已被否定的点"）也注入提示词，让改进有延续性。

**9. 结构化输出改用更可靠的通道**
现在靠 `PydanticOutputParser` + 正则提取 + 手动类型容错（这也是之前"解析降级"的根因所在）。更稳的做法是：
- 优先用模型的 **JSON mode / structured output**（OpenAI 系支持 `response_format`），
- 或 **function calling / tool** 强制模型走工具参数来返回 `CritiqueResult`。
→ 这比"祈祷模型输出干净 JSON"可靠一个数量级。

**10. Critic 分级（README 已列方向）**
弱模型初筛（快、便宜）+ 分数临界时用强模型终审，兼顾成本与质量。你们现在 `CRITIC_MODEL=mimo-v2.5` 频繁降级，正是这个优化的现实动机。

**11. 多 Critic 并行审查**
多个不同领域/视角的 Critic 同时审，取问题并集。适合 design/code 这种多维度任务。

## P3 级：产品化与可观测性

**12. 成本/耗时可观测面板**
Web 已有点评分数趋势，但没有每轮的 **token 消耗、耗时、累计成本**。补上能让用户直观看到"这轮花了多少钱、为什么停"。

**13. 人工介入（HITL）**
达到 `max_rounds` 仍不收敛时，不直接返回"历史最优"，而是推给人工确认/接管。这是从"玩具"到"生产可用"的关键一步。

---

## 我的推荐执行顺序

如果只做 3 件事，按性价比排：

1. **P0-1/2（token 预算 + 流式统计）** —— 直接关系成本和正确性，改动小、收益大。
2. **P2-8（Generator 全局记忆）** —— 最可能提升产出质量，且是纯 prompt/传参改动。
3. **P2-9（结构化输出改 JSON mode/function calling）** —— 根治"解析降级"，一次投入长期受益。

需要的话，我可以直接从其中某一条开始动手实现。我建议先做 **P0-1/2 的 token 统计与预算**（改动最集中、风险最低），或者如果你想先看到质量提升，就做 **P2-8 的 Generator 历史记忆**。你想先做哪个？
