# Generator-Critic Agent 开发计划

> 版本：2026-08-31
> 目标：将当前原型完善为可稳定演示、可量化验证、适合写入 AI 应用开发简历的项目。

## 1. 项目定位与范围

### 1.1 对外定位

本项目不是仅面向代码仓库的 Agent，也不是泛泛的“多 Agent 聊天应用”。目标定位为：

> **通用的生成-评审迭代 Agent 平台。** 支持代码、文档和方案类任务；其中代码任务通过真实测试、Lint 和构建结果形成可验证的自动修复闭环。

对简历和演示而言，代码模式是主场景，因为测试结果能客观证明改进是否有效；文档和方案模式用于证明核心编排器具有可扩展性。

### 1.2 本期范围

本计划覆盖以下三种模式：

| 模式 | 输入与产物 | 验证方式 | 本期目标 |
|---|---|---|---|
| 代码 | 代码仓库、修复或功能需求 | `pytest`、Lint、构建命令 | 完整自愈闭环与量化评估 |
| 文档 | Markdown/技术文档/报告 | 格式、必填章节、长度、链接等规则 | 一个可演示的轻量案例 |
| 方案 | PRD/技术方案/任务计划 | JSON Schema、字段完整性、依赖关系检查 | 一个可演示的轻量案例 |

### 1.3 明确不做的内容

- 本期不实现多租户、账号体系、云端任务队列或生产级权限系统。
- 本期不把 `dsh-plugin-gc-review` 纳入改造；它是独立插件子模块。
- 本期不优先做多 Critic 并行、复杂记忆系统或任意第三方工具市场。
- 不把 LLM 自评分数当成唯一成功标准；核心结论必须由可复现的验证证据支持。

## 2. 当前基线

### 2.1 已有能力

- `Orchestrator` 已实现 Generator → Critic → 收敛的主循环，并支持停止、Token 预算、历史最优草稿回退。
- `SelfHealingOrchestrator` 已实现“生成/修复 → 执行验证命令 → 注入失败日志 → 复跑”。
- `CommandRunner` 提供测试、Lint、任意命令和 Python 脚本执行能力。
- `TaskManager`、`TaskPlanner`、`TaskExecutor` 提供长任务拆解、执行和 JSON 检查点存储。
- FastAPI 后端提供 REST/SSE；Vue 前端提供工作台、任务列表和任务详情页面。
- 后端 Mock LLM 单元测试已覆盖核心模块，可在 `agentchat` Python 环境中运行。

### 2.2 已确认问题

| 优先级 | 问题 | 影响 |
|---|---|---|
| P0 | 前端 `npm run build` 因任务摘要类型不匹配而失败 | 不能作为完整 Web 产品稳定展示 |
| P0 | 服务启动依赖真实 `OPENAI_API_KEY` | 面试/本地演示受网络、密钥和模型服务影响 |
| P1 | 工作台请求直接修改全局收敛阈值配置 | 并发任务可能互相污染运行参数 |
| P1 | 文档、前端与后端之间缺少自动化契约检查 | 现有接口字段漂移已导致构建失败 |
| P1 | 文件路径校验未解析符号链接 | 工作区内的链接可能绕过目录边界 |
| P2 | benchmark 只有框架，尚无可引用的标准任务集和结果报告 | 无法证明闭环优于单次生成 |
| P2 | 无前端自动化测试与 Demo 数据 | 演示回归风险高 |

### 2.3 开发环境约定

- 后端测试使用 `D:\software\ProgramTool\Miniconda3\envs\agentchat\python.exe`。
- 前端使用 `frontend/` 下的 npm 脚本。
- 每个里程碑完成前必须运行后端测试、前端构建和本里程碑新增测试。

## 3. 目标架构

核心循环保持通用，但将“验证”抽象为显式边界：

```text
任务
  → Generator（生成或修改）
  → Critic（提出问题与改进建议）
  → Verifier（产生确定性或规则化证据）
  → Feedback Builder（组合审查意见与验证证据）
  → 下一轮 Generator，或返回最终结果
```

### 3.1 新增统一数据契约

新增 `VerificationResult`，由所有验证器返回：

| 字段 | 含义 |
|---|---|
| `passed` | 验证是否通过 |
| `score` | 可选的规则得分，范围 0–100 |
| `findings` | 可操作的问题列表 |
| `evidence` | 原始或截断后的测试输出、检查报告等依据 |
| `duration_seconds` | 验证耗时 |
| `verifier` | 验证器名称 |
| `metadata` | 命令、规则版本、退出码等补充信息 |

现有 `CommandResult` 不删除；代码验证器负责把它适配为 `VerificationResult`。这样可保留现有工具接口，避免无关重构。

### 3.2 验证器实现顺序

1. `CodeVerifier`：封装现有 `CommandRunner`，支持测试、Lint、构建命令。
2. `DocumentVerifier`：检查 Markdown 标题、必填章节、字数、链接格式等确定性规则。
3. `PlanVerifier`：校验 JSON Schema、必填字段、子任务依赖是否存在循环。

### 3.3 运行参数原则

`threshold`、最大轮数、Token 预算、验证器及验证规则必须作为单次运行参数传递，不得修改全局配置单例。运行记录必须保存当次参数，保证结果可追溯。

## 4. 里程碑计划

## M0：建立可展示的基线（第 1 周）

**目标：** 任意开发者在无真实 API Key 的情况下也能启动项目、通过构建并完成一次演示。

### 工作项

1. 修复任务列表摘要接口的前后端类型契约。
   - 为列表项与任务详情定义不同 TypeScript 类型，或由后端统一响应形状。
   - 修复 `TaskList.vue` 对 `completed_subtasks`、`subtask_count` 的访问。
2. 实现 Demo/Mock 模式。
   - 在配置中明确 `DEMO_MODE` 或等价开关。
   - 使用预置 Generator/Critic 响应与验证结果，完整推送 SSE 事件。
   - Demo 不读取真实 API Key，也不修改用户真实工作区。
3. 增加最小系统自检。
   - 后端 API 冒烟测试：应用可创建、关键路由可注册。
   - 前端构建命令纳入统一验证说明或 CI。
4. 更新快速开始文档，给出真实模式和 Demo 模式的两条路径。

### 验收标准

- `npm run build` 成功。
- `agentchat` 环境下 `pytest tests -q` 成功。
- Demo 模式下可在浏览器看到生成 token、Critic 结果、验证结果和最终结束事件。
- 用户无需提供 API Key 即可完成上述演示。

## M1：抽象验证层并统一反馈（第 2 周）

**目标：** 让编排器能够使用不同验证器，而不仅能调用代码命令。

### 工作项

1. 在 `backend/src/models/` 新增 `VerificationResult` 等必要模型。
2. 在 `backend/src/verification/` 或与现有工具层一致的位置定义最小 `Verifier` 协议。
3. 实现 `CodeVerifier`，复用 `CommandRunner`。
4. 在 `Orchestrator` 或新增反馈组装器中，将 Critic 结果和 `VerificationResult.evidence` 合并为下一轮输入。
5. 记录每轮验证结果、耗时、命令和停止原因到 `IterationRecord`/Checkpoint。
6. 覆盖以下测试：通过、失败、超时、无验证器、验证失败后继续修复。

### 验收标准

- 代码自愈不再只依赖 `SelfHealingOrchestrator` 的独立循环，而能复用统一反馈模型。
- 失败测试日志会出现在下一轮 Generator 的输入中。
- 每轮结果可从 API 或检查点读取验证证据。

## M2：补齐两类通用场景（第 3 周）

**目标：** 用最小增量证明架构可支持非代码任务。

### 工作项

1. 实现 `DocumentVerifier`。
   - 使用可配置规则：必填标题、最小/最大字数、Markdown 链接格式、禁止占位词。
   - 不引入主观 LLM 评分作为通过条件。
2. 实现 `PlanVerifier`。
   - 对计划 JSON 做 Schema 校验。
   - 检查子任务 ID 唯一性、依赖存在性、依赖图无环。
3. 各增加一个 Demo 案例和单元测试。
4. 在工作台中展示验证器名称、结果、问题及 evidence 摘要。

### 验收标准

- 相同的编排入口可运行代码、文档、方案三类任务。
- 至少两个非代码案例能在 Demo 模式下完整复现。
- 文档和方案任务有确定性规则失败案例，而非仅展示“分数变高”。

## M3：可靠性、隔离与可观测性（第 4 周）

**目标：** 使运行结果可解释、参数不串扰、文件操作边界清晰。

### 工作项

1. 将工作台的 `threshold` 等参数改为运行级配置对象，移除对全局配置的写入。
2. 强化 `FileWorkspace`。
   - 使用真实路径解析校验符号链接边界。
   - 在删除、写入和编辑事件中记录相对路径与操作摘要。
3. 完善运行指标。
   - 每轮输入/输出 Token、总 Token、验证耗时、总耗时。
   - 若模型未返回 usage，则明确标记“不可用”，不伪造 0。
4. 前端任务详情展示时间线：生成、审查、验证、修复、停止。
5. 为运行级配置并发隔离与文件链接越界增加回归测试。

### 验收标准

- 两个并发任务使用不同阈值时，彼此结果不受影响。
- 通过工作区内符号链接访问外部路径会被拒绝。
- 每一次结束都能解释停止原因与成本数据是否可用。

## M4：建立可复现评估（第 5 周）

**目标：** 证明“验证驱动迭代”优于单次生成，而不是仅展示架构。

### 工作项

1. 建立小型基准集。
   - 代码：8–15 个带固定测试的 Bug 修复/小功能任务。
   - 文档：3–5 个带固定规则的生成任务。
   - 每个任务记录初始状态、验证命令、预期结果和风险说明。
2. 设计实验组。
   - A：单次 Generator。
   - B：Generator + Critic。
   - C：Generator + Critic + Verifier。
3. 固定模型、提示词版本、最大轮数、Token 预算和运行日期。
4. 输出机器可读原始结果与 Markdown 汇总报告。
5. 统计：通过率、平均迭代轮数、平均耗时、Token、单任务失败原因。

### 验收标准

- 基准任务可以由另一位开发者在相同配置下复跑。
- README 中只引用有原始数据支撑的结论。
- 报告同时展示收益与代价，例如成功率提升对应的 Token/耗时增加。

## M5：产品演示与简历交付（第 6 周）

**目标：** 让项目在 90 秒内说明问题、方法、证据和结果。

### 工作项

1. 重写 README 首屏。
   - 一句话价值主张。
   - 架构图。
   - 三模式说明，强调代码为主验证场景。
   - 一键 Demo、真实模式、测试和 benchmark 命令。
2. 制作 60–90 秒演示。
   - 展示一个失败测试。
   - 展示 Agent 修改、验证失败日志回注和测试最终通过。
   - 展示一个文档或方案规则校验案例。
3. 优化首页信息层级。
   - 展示任务状态、每轮证据、成本、停止原因。
   - 突出“单次生成 vs 验证驱动迭代”的结果，而不是罗列技术名词。
4. 整理简历描述、项目亮点和面试讲解稿。

### 验收标准

- 新读者能在 README 中找到定位、运行方式、证据和限制。
- 演示不依赖私有数据、真实密钥或不可控外部仓库。
- 简历描述中的每项指标均可追溯至 benchmark 报告。

对于涉及接口字段的改动，必须同时增加：

3. 至少一个消费该接口的前端构建/组件测试。

对于涉及 Agent 行为的改动，必须同时增加 Mock LLM 测试；对于“验证成功/失败”的产品结论，必须增加确定性验证器测试，不依赖真实模型评分。

## 7. 风险与决策原则

| 风险 | 应对原则 |
|---|---|
| LLM 输出不稳定 | 结构化输出优先；失败时保存原始响应和降级原因 |
| 模型服务不可用 | Demo/Mock 模式必须覆盖核心用户旅程 |
| 验证成本过高 | 使用总/单轮 Token 预算、验证超时和最大轮数 |
| 无法证明效果 | 先做小而可复现的 benchmark，再扩大任务集 |
| 过度抽象 | 每新增一种验证器只实现最小协议，不提前做插件市场 |
| 文件操作风险 | 工作区隔离、真实路径校验、操作审计、Demo 禁止真实写入 |

## 8. 完成定义

本计划完成时，项目应同时满足：

- 前后端可稳定构建，且无 API Key 可运行 Demo。
- 同一个编排核心支持代码、文档和方案任务。
- 代码任务能展示“失败证据 → 修复 → 验证通过”的完整闭环。
- 每轮都有可追溯的审查、验证、耗时和 Token 信息。
- 有可复现的 benchmark 数据，能够比较至少三种执行策略。
- README、Demo 和简历描述只陈述可运行、可验证、可复现的能力与指标。
