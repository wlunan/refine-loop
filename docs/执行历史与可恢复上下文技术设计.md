# 执行历史与可恢复上下文技术设计

> 文档状态：Phase 1-4 已完成，Phase 5 前端回放待实现
>
> 目标：为 Generator、Critic、ToolAgent 和长任务执行器增加可追溯的执行历史，并支持从最近一次安全检查点恢复任务。
>
> 本文是实现设计与当前状态说明。当前实现已经有任务状态、轮次检查点、Trace 事件和 artifact，并已实现执行历史模型、JSONL 存储、ToolAgent 消息状态快照、工具调用生命周期记录、文件操作幂等恢复判定和恢复入口；前端完整回放仍待实现。

## 1. 背景与问题

当前系统已经具备以下能力：

- `Task`、`SubTask` 和 `TaskStatus` 持久化。
- 每轮生成、Critic 评分、问题、建议和验证结果保存为 `Checkpoint`。
- 任务事件以 JSONL 保存，并通过 Timeline、SSE 和 artifact 对外展示。
- Git 任务可以保留隔离 worktree。
- 后端重启后，运行中的任务会被转换为 `paused`，之后可以重新启动。

但当前恢复仍然是“重新执行未完成子任务”，不是完整的 Agent 上下文恢复，原因如下：

1. `TaskExecutor.execute()` 每次都会新建 `Orchestrator`。
2. `ToolAgent.run()` 内部的 `messages` 只存在于单次调用的局部变量中。
3. `Checkpoint` 没有保存执行阶段、消息历史、工具调用状态和恢复位置。
4. 工具执行前后没有统一的持久化事务边界。
5. 文件工具和验证工具没有统一的幂等恢复协议。

因此需要将“执行历史”和“可恢复状态”分开设计：

- **执行历史**回答：Agent 做了什么、模型看到了什么、工具返回了什么。
- **恢复快照**回答：任务现在处于哪一步、恢复后从哪里继续、哪些动作不能重复执行。

## 2. 目标与非目标

### 2.1 目标

1. 保存 Generator、Critic 和 ToolAgent 的结构化消息历史。
2. 保存每次模型调用、工具调用、验证和状态转换的执行记录。
3. 为每个关键执行阶段建立可持久化检查点。
4. 后端重启或任务暂停后，从最近安全边界恢复。
5. 已完成子任务不重复执行。
6. 对文件工具支持基于文件状态的幂等重放判断。
7. 对不可确认副作用的命令禁止自动重放。
8. 为前端提供可回放的执行时间线和消息详情。
9. 保留现有 Timeline、artifact 和 Checkpoint API 的兼容性。

### 2.2 非目标

以下能力不属于本次设计目标：

- 从 LLM 流式输出的任意 token 位置继续同一个 HTTP 请求。
- 恢复供应商内部的模型服务端会话。
- 使用 pickle 保存 LangChain Message 对象。
- 在没有幂等证据时自动重放任意 Shell 命令。
- 把 JSON 文件存储直接升级为分布式数据库。
- 将本地工作区变成操作系统级代码执行沙箱。

正确的恢复语义是：

> 只能从最近一次已经持久化的安全检查点继续，不能承诺恢复到任意 token 或任意系统调用位置。

## 3. 术语与恢复语义

| 术语 | 含义 |
|---|---|
| Task | 用户提交的一次长任务，可能包含多个子任务 |
| SubTask | 任务计划中的一个可执行单元 |
| Attempt | 一个子任务的一次执行尝试；暂停恢复后产生新的 attempt |
| Round | Generator-Critic 的一轮迭代 |
| Step | ToolAgent 的一次模型决策或工具处理步骤 |
| Execution Record | 描述一次执行动作的追加式历史记录 |
| Conversation Message | 可重建的 system/human/ai/tool 消息 |
| Execution Snapshot | 描述当前恢复位置的完整快照 |
| Safe Boundary | 动作结果和状态均已持久化，可以恢复的执行边界 |
| Unknown Side Effect | 动作可能已经产生副作用，但持久化状态不足以证明结果 |

### 3.1 恢复级别

#### Level 1：子任务级恢复

已完成的子任务不重复执行，未完成子任务从头重新开始，但复用已有工作区文件。

这是当前代码接近具备的能力，也是第一阶段的兼容兜底模式。

#### Level 2：轮次级恢复

恢复最近一轮 Generator 输出、Critic 结果、验证结果和轮次状态，从下一轮开始继续。

```text
第 2 轮 round_committed
        ↓
恢复任务
        ↓
从第 3 轮 Generator 开始
```

#### Level 3：工具调用级恢复

恢复 ToolAgent 的消息队列、工具调用记录和当前工具步骤。已完成的幂等文件操作不重复执行，未完成操作根据文件状态判断是否重放。

```text
tool_call_pending
        ↓
tool_executing
        ↓
tool_completed
        ↓
继续下一次模型决策
```

### 3.2 崩溃恢复原则

模型调用过程中崩溃：

- 不能恢复同一个模型请求。
- 丢弃未持久化的模型响应。
- 从上一个安全检查点重新发起模型调用。

工具调用过程中崩溃：

- 如果工具状态为 `completed` 且结果已保存，不重放。
- 如果工具状态为 `running` 或 `unknown`，根据工具类型决定重放、检查或人工确认。
- 对无法判断副作用的命令，默认停止自动恢复。

### 4.1 责任边界

| 模块 | 新增责任 | 不应负责 |
|---|---|---|
| `TaskManager` | 任务级恢复入口、attempt 管理、恢复冲突处理 | 解析 LLM 消息 |

| `FileWorkspace` | 文件状态检查、操作幂等判断所需的事实 | 保存任务快照 |
| `StateStore` | 原子写入和查询历史 | 决定恢复策略 |
| 前端 | 展示执行历史和恢复状态 | 自行推断恢复安全性 |

### 5.2 消息模型

不要持久化 LangChain Message 实例，使用稳定的项目内模型：

```python
class ConversationMessage(BaseModel):
    id: str
    task_id: str
    subtask_id: str
    attempt_id: str
    sequence: int = Field(ge=0)
    agent: Literal["generator", "critic", "tool_agent"]
    role: Literal["system", "human", "ai", "tool"]
    content: str | list[dict]
    tool_call_id: str | None = None
    tool_calls: list[dict] = Field(default_factory=list)
    name: str | None = None
    round: int = Field(default=0, ge=0)
    step: int = Field(default=0, ge=0)
    created_at: datetime = Field(default_factory=datetime.now)
```

#### 序列化要求

需要实现两个方向的转换：

```python
def serialize_message(message: BaseMessage) -> ConversationMessage:
    ...


def deserialize_message(message: ConversationMessage) -> BaseMessage:
    ...
```

至少支持：

- `SystemMessage`
- `HumanMessage`
- `AIMessage`
- `ToolMessage`

需要保留：

- `content`
- `tool_call_id`
- `tool_calls`
- 工具名称
- 消息顺序

不应保存：

- API Key。
- 完整环境变量。
- 未经脱敏的认证头。
- 与恢复无关的供应商私有对象。

### 5.4 工作区指纹

```python
class FileFingerprint(BaseModel):
    path: str
    size: int
    sha256: str


class WorkspaceFingerprint(BaseModel):
    root: str
    files: list[FileFingerprint] = Field(default_factory=list)
    digest: str
    created_at: datetime = Field(default_factory=datetime.now)
```

指纹计算建议：

1. 只扫描允许访问的文件。
2. 排除 `.git`、`node_modules`、`__pycache__` 和 `.pytest_cache`。
3. 按相对路径排序。
4. 对路径、文件大小和 SHA-256 组合后再次计算整体 digest。
5. 记录文件数量和总大小，防止恢复时扫描无限扩大。

### 5.5 执行快照

```python
class ExecutionSnapshot(BaseModel):
    task_id: str
    subtask_id: str
    attempt_id: str
    snapshot_id: str
    version: int = 1

    phase: ExecutionPhase
    round: int = Field(default=0, ge=0)
    step: int = Field(default=0, ge=0)

    task_prompt: str
    draft: str = ""
    critique: CritiqueResult | None = None
    messages: list[ConversationMessage] = Field(default_factory=list)
    tool_records: list[ToolExecutionRecord] = Field(default_factory=list)

    workspace_path: str
    workspace_fingerprint: WorkspaceFingerprint | None = None
    total_tokens: int = Field(default=0, ge=0)

    resumable: bool = True
    recovery_note: str | None = None
    created_at: datetime = Field(default_factory=datetime.now)
```

完整消息可以放在独立 JSONL 中，快照只保存：

- 最近消息序号。
- 最近安全阶段。
- 消息文件位置或 sequence 范围。
- 最近工具记录范围。

这样避免每次保存快照都复制全部消息。

```python
class ExecutionAttempt(BaseModel):
```

### 6.2 JSONL 记录格式

`messages.jsonl` 每行一条消息：

```json
{
  "id": "msg_001",
  "task_id": "task_1234",
  "subtask_id": "subtask_1",
  "attempt_id": "attempt_001",
  "sequence": 7,
  "agent": "tool_agent",
  "role": "tool",
  "content": "已修改文件: src/app.py",
  "tool_call_id": "call_003",
  "tool_calls": [],
  "round": 1,
  "step": 3,
  "created_at": "2026-09-06T12:00:00"
}
```

`tools.jsonl` 每行一条工具执行记录。

`attempts.jsonl` 每行一条 Attempt 生命周期记录，记录恢复和结束原因。

### 6.3 原子写入

快照写入必须遵循：

```text
写入 snapshot.tmp
→ flush
→ fsync
→ 原子替换 snapshot.json
```

Windows 下使用 `os.replace()` 完成最终替换。

JSONL 追加写入应：

- 每条记录写入后 flush。
- 关键安全边界执行 fsync。
- 读取时跳过损坏行并记录告警。
- sequence 必须单调递增。

## 7. 执行历史记录协议

### 7.1 Generator-Critic 文本模式

一轮执行的保存顺序：

```text
1. 保存 Generator 请求消息
2. 保存 phase=generating 快照
3. 调用 Generator
4. 保存 Generator 响应消息
5. 保存 Critic 请求消息
6. 保存 phase=critic_pending 快照
7. 调用 Critic
8. 保存 Critic 原始响应
9. 保存结构化 CritiqueResult
10. 保存 phase=critic_completed 快照
11. 保存 round_committed 快照
```

必须同时保存：

- 模型原始响应。
- 解析后的 `CritiqueResult`。
- 模型名称。
- token 用量。
- 调用耗时。
- 错误信息（如有）。

原始响应和大文本建议作为 artifact 保存，消息记录中保存引用和必要摘要。

### 7.2 ToolAgent 文件模式

单次工具调用的保存顺序：

```text
1. 保存模型请求消息
2. 调用模型
3. 保存模型响应消息
4. 保存 tool_call_pending
5. 保存工具参数和幂等键
6. 保存 tool_executing
7. 执行工具
8. 保存工具结果
9. 保存 ToolMessage
10. 保存 tool_completed
11. 进入下一次模型决策
```

严格禁止只在工具执行结束后保存一条记录。否则进程崩溃时无法判断工具是否已经开始执行。

### 7.3 验证步骤

验证结果属于可重复执行记录：

```text
保存 phase=verifying
→ 执行 pytest / ruff / npm build
→ 保存 VerificationSummary
→ 保存验证 artifact
→ 保存 round_committed
```

pytest、ruff 和构建命令默认可以重新执行；具有外部副作用的自定义命令必须被标记为 `unknown`。

## 8. ToolAgent 改造

当前 [tool_agent.py](../backend/src/agents/tool_agent.py) 的 `messages` 是局部变量。需要让执行状态由外部传入和导出。

### 8.1 新接口

```python
class ToolAgentResult(BaseModel):
    output: str
    state: ToolAgentState


class ToolAgentState(BaseModel):
    messages: list[ConversationMessage] = Field(default_factory=list)

```

建议接口：

```python
def run(
    self,
    user_message: str,
    execution_state: ToolAgentState | None = None,
    checkpoint_callback: Callable[[ToolAgentState], None] | None = None,
) -> ToolAgentResult:
    ...
```

### 8.2 主循环伪代码

```python
state = execution_state or create_initial_state(user_message)

while state.current_step < self.max_steps:
    checkpoint_callback(state.with_phase("generating"))

    response = invoke_model(deserialize_messages(state.messages))
    ai_message = serialize_message(response)
    state.messages.append(ai_message)
    persist_message(ai_message)

    if response.tool_calls:
        records = create_pending_tool_records(response.tool_calls)
        state.pending_tools.extend(records)
        checkpoint_callback(state.with_phase("tool_call_pending"))

        for record in state.pending_tools:
            recovered = recover_tool_if_needed(record, state)
            if recovered is not None:
                result = recovered
            else:
                record.status = "running"
                checkpoint_callback(state.with_phase("tool_executing"))
                result = execute_tool(record)

            record.result = result
            record.status = "completed"
            persist_tool_record(record)
            tool_message = create_tool_message(record)
            state.messages.append(tool_message)
            persist_message(tool_message)
            checkpoint_callback(state.with_phase("tool_completed"))

        state.pending_tools.clear()
        state.current_step += 1
        continue

    state.phase = "completed"
    checkpoint_callback(state)
    return ToolAgentResult(output=content, state=state)

state.phase = "failed"
state.resumable = False
checkpoint_callback(state)
return ToolAgentResult(output=last_content, state=state)
```

### 8.3 重要约束

- 每次模型调用前保存状态，便于识别正在调用模型。
- 每个工具调用必须有稳定 `call_id`。
- 同一个 `call_id` 只能有一个最终完成记录。
- `ToolMessage` 必须保留对应 `tool_call_id`。
- 不要通过 `dir()`、字符串猜测或模型输出推断恢复位置。

## 9. 文件工具幂等恢复

文件工具的恢复必须基于实际文件状态，而不是只看历史日志。

### 9.1 `write_file`

调用前记录：

```text
path
目标内容 SHA-256
目标内容长度
执行前文件 SHA-256（如果存在）
```

恢复时：

```text
当前文件 hash == 目标 hash → 视为已完成
当前文件 hash == 执行前 hash → 可以重放
两者都不满足 → 文件冲突，停止自动恢复
```

### 9.2 `edit_file`

调用前记录：

```text
old_text hash
new_text hash
执行前文件 hash
```

恢复时：

```text
新文本已经存在且文件状态匹配 → 视为完成
旧文本仍唯一存在 → 可以重放
旧文本和新文本都不满足 → 标记冲突
```

### 9.3 `delete_file`

恢复时：

```text
目标不存在 → 视为已完成
目标仍存在且 hash 匹配执行前状态 → 可以删除
目标存在但 hash 不匹配 → 拒绝删除
```

### 9.4 只读工具

以下工具可以安全重复执行：

```text
list_directory
read_file
search_files
```

但每次恢复重放仍需生成新的执行记录，不能修改旧记录。

### 9.5 验证工具

以下工具一般可以重放：

```text
run_tests
run_lint
run_python
npm run build
```

需要记录：

- 工作区 fingerprint。
- 命令 profile。
- 超时时间。
- stdout/stderr 摘要。
- 退出码。

### 9.6 任意自定义命令

对于以下情况默认不可自动恢复：

- 修改数据库。
- 发送网络请求。
- 发布或推送代码。
- 改变系统配置。
- 创建外部资源。
- 无法识别副作用的脚本。

恢复状态设置为：

```text
unknown_side_effect
```

任务进入等待人工确认状态，而不是自动重放。

## 10. Orchestrator 改造

当前 [orchestrator.py](../backend/src/orchestrator/orchestrator.py) 可以保留现有 `run()` 和 `run_with_files()` API，增加可选恢复状态。

### 10.1 文本模式恢复

```python
def run(
    self,
    task: str,
    initial_draft: str = "",
    resume_state: AgentState | None = None,
) -> RunResult:
    ...
```

恢复时：

1. 加载最近 `round_committed` 快照。
2. 恢复 `draft`、`critique`、`current_round`、历史评分和 token 用量。
3. 从下一轮 Generator 开始。
4. 不重复调用已经完成的 Critic。
5. 如果快照处于 `critic_pending`，重新执行该轮 Critic 或回退到该轮 Generator，具体由快照完整性决定。

### 10.2 文件模式恢复

文件模式优先恢复 ToolAgent 状态：

```text
加载 ExecutionSnapshot
→ 验证 workspace fingerprint
→ 恢复消息序列
→ 处理 pending tool
→ 继续 ToolAgent
```

如果消息历史缺失或无法反序列化，必须降级为轮次恢复或子任务重启，并在恢复结果中标记：

```text
recovery_mode = "round" 或 "restart"
```

## 11. TaskExecutor 改造

当前 [task_executor.py](../backend/src/executor/task_executor.py) 的 `execute()` 需要增加恢复路由。

### 11.1 执行入口

```python
snapshot = store.load_latest_execution_snapshot(task_id, subtask.id)

if snapshot is None:
    mode = "fresh"
elif snapshot.phase == "round_committed":
    mode = "round"
elif snapshot.phase == "tool_completed":
    mode = "tool"
elif snapshot.phase in {"tool_call_pending", "tool_executing"}:
    mode = recover_pending_tool(snapshot)
elif snapshot.phase == "completed":
    return restore_completed_subtask(snapshot)
else:
    mode = "restart"
```

### 11.2 恢复前检查

恢复前必须检查：

1. 任务仍处于 `PAUSED` 或可恢复状态。
2. 当前子任务没有被其他线程执行。
3. execution workspace 仍存在。
4. workspace fingerprint 与快照相容。
5. 没有未处理的未知副作用工具。
6. 快照 JSON 和消息 JSONL 可以完整读取。
7. 当前任务配置与快照版本兼容。

### 11.3 Attempt 生命周期

恢复不能继续复用旧的运行线程。每次恢复创建新的 `attempt_id`：

```text
attempt_001: fresh → paused
attempt_002: resume from snapshot_008 → completed
```

旧 Attempt 只读保存，不覆盖。

### 11.4 暂停顺序

正确顺序：

```text
收到暂停请求
→ 设置 stop event
→ 当前调用完成或进入可停止边界
→ 写入 paused snapshot
→ 更新 Task.status=paused
→ 清理执行器引用
```

如果模型调用本身阻塞，不能强制杀死调用线程；应在请求返回后立即检查停止标记，并在下一个安全边界停止。

## 12. TaskManager 改造

当前 [task_manager.py](../backend/src/manager/task_manager.py) 的 `resume_task()` 会重新启动执行流程。改造后仍可保留该接口，但需要：

1. 加载最近执行快照。
2. 生成新的 `attempt_id`。
3. 把恢复模式写入任务事件。
4. 将 snapshot 传给 `TaskExecutor`。
5. 如果无法安全恢复，返回明确错误或降级为重新执行。

建议增加：

```python
def get_resume_state(self, task_id: str) -> ResumeState:
    ...


def resume_task(
    self,
    task_id: str,
    mode: Literal["auto", "round", "restart"] = "auto",
) -> None:
    ...
```

`auto` 的决策顺序：

```text
tool-level → round-level → subtask restart
```

只有在用户明确选择 `restart` 时，才清除当前子任务的恢复上下文；不能默认删除历史。

## 15. 故障恢复矩阵

| 崩溃位置 | 最后持久化状态 | 恢复行为 |
|---|---|---|
| 模型调用前 | `generating` | 重新发起当前模型调用 |
| 模型响应已收到 | `model_response_received` | 使用已保存响应，不重复调用 |
| 工具执行前 | `tool_call_pending` | 创建或检查工具记录 |
| 工具执行中 | `tool_executing` | 根据工具类型判定重放或阻断 |
| 工具结果已保存 | `tool_completed` | 不重复执行，继续下一步 |
| Critic 调用前 | `critic_pending` | 重新调用 Critic |
| Critic 结果已保存 | `critic_completed` | 直接提交轮次 |
| 验证执行中 | `verifying` | 对可重复验证重新执行 |
| 轮次已提交 | `round_committed` | 从下一轮继续 |
| 子任务已提交 | `subtask_committed` | 不重复执行子任务 |
| 自定义命令未知 | `unknown_side_effect` | 阻断自动恢复，要求确认 |

注意：`model_response_received` 只有在完整模型响应已经持久化时才成立。流式输出中途不能把部分文本当作完整响应。

## 16. 数据一致性与并发控制

### 16.1 单任务互斥

同一个 `task_id` 同时只能有一个执行 Attempt。现有 `_task_locks` 可以继续使用，但需要覆盖：

- start。
- pause。
- resume。
- cancel。
- rollback。

### 16.2 任务版本号

建议给 `Task` 增加：

```python
state_version: int = 0
```

保存时使用 compare-and-swap 语义：

```text
读取 version=10
更新成功后 version=11
如果磁盘已经是 version=11，拒绝旧对象覆盖
```

至少在恢复、暂停和完成子任务时使用版本检查。

### 16.3 事件顺序

事件应包含：

```text
sequence
attempt_id
snapshot_id
```

前端按 `sequence` 排序，不按网络到达顺序排序。SSE 断线重连时可以使用 `after` 参数补齐遗漏记录。

## 17. 隐私、容量与清理

### 17.1 敏感信息

执行历史可能包含：

- 文件内容。
- 模型上下文。
- 环境配置。
- 命令参数。

因此：

- `.env`、私钥、密码和 token 文件默认禁止读取或脱敏。
- 日志中不记录 API Key。
- 工具参数中的凭证字段需要脱敏。
- 错误信息不应包含完整环境变量。

### 17.2 容量限制

建议配置：

```text
最大消息条数：10000 / 子任务
最大单条消息：100000 字符
最大 artifact：20 MB
最大任务历史：200 MB
最大执行尝试：50 / 子任务
```

超过限制后：

- 压缩旧消息为摘要。
- 保留恢复所需的最近快照。
- 保留完整工具参数和结果的 artifact 引用。
- 不删除尚未完成任务的最近安全检查点。

### 17.3 删除策略

删除任务时同步删除：

```text
tasks
checkpoints
events
artifacts
executions
```

正在运行或可恢复任务必须先取消或明确丢弃，避免留下孤立 worktree 和执行历史。

## 18. 分阶段实施计划

### Phase 1：执行历史可查看

改动范围：

```text
backend/src/models/execution.py
backend/src/store/state_store.py
backend/src/executor/task_executor.py
backend/src/manager/task_manager.py
backend/routers/tasks.py
```

实现：

- `ConversationMessage`。
- `ExecutionRecord`。
- Generator/Critic 的请求、响应记录。
- JSONL 存储。
- 执行历史 API。
- 删除任务时清理历史。

验收：

- 任务详情可以查看每一轮 Generator 和 Critic 记录。
- 工具参数和工具结果可以通过 artifact 查看。
- 旧任务 JSON 仍可正常加载。

### Phase 2：轮次级恢复

实现：

- 扩展 `Checkpoint` 或新增 `ExecutionSnapshot`。
- 保存执行阶段、attempt_id、workspace fingerprint。
- `TaskExecutor` 加载最新轮次快照。
- 恢复后从下一轮 Generator 开始。
- 增加恢复状态 API。

验收：

- 第 2 轮完成后模拟进程重启。
- 恢复从第 3 轮开始。
- 第 1、2 轮不重复调用。
- 已完成子任务不重复执行。

### Phase 3：消息上下文恢复

实现：

- LangChain Message 序列化和反序列化。
- Generator、Critic 和 ToolAgent 使用外部消息状态。
- 恢复时重建消息列表。
- 不可解析消息时降级为轮次恢复。

验收：

- 恢复后的模型输入包含恢复前已保存消息。
- `AIMessage.tool_calls` 和 `ToolMessage.tool_call_id` 保持一致。
- 供应商 Message 对象不直接写入磁盘。

### Phase 4：工具调用级恢复

实现：

- `ToolExecutionRecord`。
- 工具调用前后检查点。
- 文件工具 hash 记录。
- write/edit/delete 幂等判断。
- 验证命令可重放。
- 未知副作用命令阻断。

验收：

- 工具执行后模拟崩溃，恢复不重复写入。
- 工具执行前模拟崩溃，恢复可以执行。
- 文件被外部修改时恢复失败并报告冲突。
- 自定义副作用命令不会自动重放。

### Phase 5：前端回放和演示

实现：

- 执行历史时间线。
- 消息和工具详情。
- 恢复状态面板。
- 从检查点恢复按钮。
- 恢复冲突和阻断原因展示。

验收：

- 用户可以看到 Agent 从任务开始到完成的完整链路。
- 用户可以区分模型消息、工具调用、验证结果和状态变化。
- 用户可以理解恢复是从哪个安全边界开始的。

## 19. 测试计划

建议新增：

```text
tests/test_execution_models.py
tests/test_message_serialization.py
tests/test_execution_store.py
tests/test_execution_history.py
tests/test_round_resume.py
tests/test_tool_resume.py
tests/test_idempotent_file_recovery.py
tests/test_resume_conflicts.py
tests/test_process_restart_recovery.py
```

### 19.1 模型和存储

- 消息模型 JSON 序列化和反序列化。
- Tool call 字段完整保留。
- JSONL 追加和读取顺序正确。
- 损坏行不会导致全部历史不可读。
- 快照原子替换不会留下半个 JSON。
- 旧版本任务文件可以迁移加载。

### 19.2 文本模式

- Generator 请求和响应都被保存。
- Critic 原始响应和结构化结果同时保存。
- 从 `round_committed` 恢复时不重复 Critic。
- 历史评分和 token 总量不丢失。

### 19.3 ToolAgent

- 原生 tool call 消息可以恢复。
- JSON 文本协议消息可以恢复。
- ToolMessage 与 tool_call_id 对应。
- 工具结果保存后不会重复执行。
- 最大工具步骤恢复后继续计数，而不是重新从 0 开始。

### 19.4 文件幂等

- `write_file` 目标 hash 已匹配时跳过。
- `write_file` 仍是旧 hash 时重放。
- `edit_file` 已完成时跳过。
- `edit_file` 发生冲突时阻断。
- `delete_file` 目标已不存在时视为完成。
- 外部修改导致 fingerprint 不匹配时阻断。

### 19.5 任务生命周期

- 暂停后生成 paused snapshot。
- 后端重启后 RUNNING 转为 PAUSED。
- 恢复生成新的 attempt_id。
- 已完成子任务不重复执行。
- 取消任务不留下孤立执行线程、worktree 或历史索引。
- 任务同时恢复两次时只有一个执行器成功获取锁。

## 20. 兼容性与迁移

### 20.1 旧 Checkpoint

旧 `Checkpoint` 缺少新字段时使用默认值：

```text
attempt_id = "legacy"
phase = "round_committed"
messages = []
resumable = false 或 round-level
```

旧检查点可以用于展示和轮次恢复，但不能直接用于 ToolAgent 级恢复。

### 20.2 旧任务

加载旧任务时：

- 保留原有 `Task` 字段。
- 不自动删除旧检查点。
- 第一次恢复时建立 `attempt_id`。
- 如果没有执行快照，降级为 `restart` 或 `round` 模式。
- 在 API 响应中返回 `recovery_mode`。

### 20.3 版本字段

所有新的持久化模型增加：

```text
schema_version
```

建议从 `1` 开始，读取时按版本执行迁移，不通过异常猜版本。

## 21. 可观测性

每次模型调用、工具调用、验证和恢复都应使用统一字段：

```text
task_id
subtask_id
attempt_id
round
step
phase
snapshot_id
sequence
duration_seconds
tokens_used
```

至少记录以下指标：

- 每个任务的恢复次数。
- 每种恢复模式的数量。
- 工具重复执行次数。
- 恢复冲突次数。
- 未知副作用阻断次数。
- 恢复成功率。
- 恢复后重新调用模型的次数。

这些指标可以用于后续 Benchmark，但不能在没有实验结果时写成简历中的提升百分比。

## 22. 风险与取舍

| 风险 | 处理方式 |
|---|---|
| 任意 token 级恢复不可行 | 只承诺安全边界恢复 |
| LangChain Message 版本变化 | 使用项目内 JSON 消息模型 |
| 工具执行后进程崩溃 | 保存 before/after hash，按工具类型恢复 |
| 文件被用户外部修改 | fingerprint 校验，冲突时阻断 |
| JSONL 长期膨胀 | artifact、摘要和容量上限 |
| 自定义命令有外部副作用 | 标记 unknown，不自动重放 |
| 多线程覆盖任务状态 | attempt_id、task version 和任务锁 |
| 消息包含敏感数据 | 敏感文件策略、脱敏和清理机制 |
| 恢复逻辑过于复杂 | 先完成轮次恢复，再实现工具级恢复 |

## 23. 推荐的最小可交付版本

如果只做一轮，建议实现以下内容：

```text
1. ConversationMessage
2. ExecutionRecord
3. StateStore JSONL 持久化
4. Generator/Critic 请求与响应记录
5. ExecutionSnapshot.phase
6. round_committed 恢复
7. workspace fingerprint
8. 执行历史 API
9. 任务重启恢复测试
```

暂时不要在第一轮实现：

- 任意 Shell 命令自动恢复。
- 完整 token 级恢复。
- 分布式数据库。
- 复杂消息压缩算法。
- 多用户共享执行历史。

## 24. 最终能力定义

实现完成后，项目可以准确描述为：

> 为 Generator、Critic 和 ToolAgent 建立结构化执行历史，持久化模型消息、工具调用、验证结果和状态转换；通过轮次级与工具调用级安全检查点恢复未完成任务，并基于文件哈希和工具幂等性判断避免重复修改工作区。

更谨慎的技术承诺是：

> 系统支持从最近一次已持久化的安全执行边界恢复，不承诺从任意 token 位置继续原始模型请求。

## 26. 完成标准

满足以下条件后，才可以在简历或项目文档中写“支持可恢复 Agent 执行”：

- [ ] Generator、Critic 和 ToolAgent 的消息可以持久化和读取。
- [ ] 消息可以转换为稳定 JSON，而不是依赖 pickle。
- [ ] 每次工具调用有 pending、running、completed 等状态。
- [ ] 每个安全边界都有快照。
- [ ] 任务恢复会生成新的 Attempt。
- [ ] 后端重启后可以恢复至少轮次级上下文。
- [ ] 文件工具具备幂等恢复判断。
- [ ] 未知副作用命令不会自动重放。
- [ ] 工作区 fingerprint 冲突会阻断恢复。
- [ ] 执行历史可以通过 API 和前端查看。
- [ ] 有故障注入测试证明恢复行为。
- [ ] 文档明确说明不能恢复任意 token 位置。

完成前述最小交付版本后，项目可以从“保存任务状态”升级为：

> **具备可追溯执行历史和基于安全检查点的 Agent 恢复能力。**
