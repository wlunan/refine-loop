# 功能开发计划与现有能力梳理

> 版本：2026-08-31  
> 文档目的：说明当前项目已经具备什么产品能力，以及后续应该新增什么功能。  
> 相关文档：[`开发计划.md`](./开发计划.md) 记录工程稳定性、演示和评估的补齐工作；本文只讨论面向用户的功能演进。

## 1. 产品目标

本项目定位为“生成-评审-验证”工作台：用户提交一个任务，系统生成结果、审查结果并在需要时使用验证证据驱动下一轮修改。

支持三类任务：

| 任务类型 | 用户目标 | 最终产物 | 关键验证 |
|---|---|---|---|
| 代码任务 | 修复 Bug、开发小功能、改造仓库 | 工作区文件变更、测试结果 | 测试、Lint、构建 |
| 文档任务 | 生成或润色 README、报告、技术文档 | Markdown/文本 | 结构、长度、链接、规则清单 |
| 方案任务 | 生成 PRD、技术方案、任务计划 | 结构化方案 | Schema、依赖关系、必填项 |

代码任务是产品的主验证场景，但不是唯一方向。文档和方案功能共享同一套 Agent 编排、审查记录和运行历史能力，只替换任务模板与验证规则。

## 2. 当前已有功能

以下结论来自现有实现，而不是规划中的设想。

## 3. 当前功能边界

为了避免把“已有代码”误写成“已交付产品”，以下能力还不算完整功能：

| 能力 | 现状 | 需要补齐的功能 |
|---|---|---|
| 可验证代码任务 | 自愈类已存在，但长任务和 Web 文件模式仍以 Critic 快照审查为主 | 在统一任务流中配置并执行测试/Lint/构建验证器 |
| 文档/方案验证 | 有领域提示词，没有独立规则验证器 | 提供规则模板、验证结果和二次修订反馈 |
| 文件模式工作台 | 后端有 `/api/stream_files`，现有工作台仅调用文本接口 | 在页面提供工作区选择、文件变更与工具调用展示 |
| 运行历史 | 有 JSON 检查点，界面只展示单任务信息 | 提供运行列表、轮次对比、结果复用和导出 |
| 评估结果 | 有 benchmark 框架，无正式任务集和可视化报告 | 提供基准集管理、策略对比和报告页面 |
| 人工审核 | 可停止，但不能在关键操作前确认 | 对写文件、删除文件、最终交付增加审批点 |

## 4. 功能路线图

功能按“先打通一个完整体验，再扩展通用场景，最后沉淀数据资产”的顺序开发。

## F1：统一任务创建与模式选择

**用户价值：** 用户可以明确选择要处理的任务类型，而不是只填写一段 prompt。

### 功能内容

1. 新建任务向导，选择“代码 / 文档 / 方案”模式。
2. 不同模式展示不同的必填项。
   - 代码：工作区、验证命令、是否允许文件写入。
   - 文档：输出格式、规则模板、初始草稿（可选）。
   - 方案：方案模板、期望 JSON Schema 或必填章节。
3. 创建后显示任务摘要：任务模式、验证规则、最大轮数和预算。
4. 后端 `Task` 增加运行模式和验证配置；保留对旧任务数据的兼容读取。

### 主要影响范围

- `backend/src/models/task.py`
- `backend/routers/tasks.py`
- `frontend/src/views/TaskList.vue`
- 新增或拆分 `frontend/src/views/TaskCreate.vue`

### 验收标准

- 三种模式均可创建任务。
- 后端会拒绝代码任务缺少工作区、文档任务缺少规则模板等无效配置。
- 创建后的任务详情能显示当前模式与配置，不依赖前端临时状态。

## F2：代码任务的验证驱动闭环

**用户价值：** 代码任务不只“被 Critic 打分”，而是通过测试是否通过来决定是否完成。

### 功能内容

1. 将现有 `SelfHealingOrchestrator` 的验证反馈能力接入长任务和文件模式运行。
2. 支持每个任务设置验证命令：`pytest`、`npm test`、`npm run build`、自定义命令。
3. 每轮执行顺序变为：文件修改 → 测试/构建 → 失败日志 → 修复反馈 → 下一轮。
4. 任务详情展示每轮验证状态、退出码、耗时和失败日志摘要。
5. 若达到最大轮数仍失败，返回最后一次文件状态和全部验证记录，而不是宣称成功。

### 主要影响范围

- `backend/src/orchestrator/self_healing.py`
- `backend/src/orchestrator/orchestrator.py`
- `backend/src/executor/task_executor.py`
- `backend/src/tools/verification.py`
- `backend/src/models/task.py`
- `frontend/src/views/TaskDetail.vue`

### 验收标准

- 预置的失败测试任务能自动修复并最终测试通过。
- 每次测试失败的关键日志会进入下一轮 Generator 输入。
- 用户能在任务详情中看到“第几轮、执行什么命令、为什么失败或通过”。

## F3：文件变更预览与人工确认

**用户价值：** 用户可以安全地使用文件模式，而不是把工作区完全交给模型。

### 功能内容

1. 展示每轮文件操作和文件变更摘要。
2. 对写入、编辑、删除提供三种策略：自动执行、仅关键操作确认、全部确认。
3. 增加“批准 / 拒绝 / 停止”交互；拒绝后将用户原因反馈给下一轮。
4. 为文件变更提供统一 diff 预览；无法生成 diff 时退化为前后内容摘要。
5. 保留操作审计记录，可从任务详情下载。

### 主要影响范围

- `backend/src/tools/filesystem.py`
- `backend/src/agents/tool_agent.py`
- `backend/routers/tasks.py`
- `frontend/src/views/TaskDetail.vue`
- 新增文件 diff/确认组件

### 验收标准

- 删除与覆盖写入在确认策略下不会直接执行。
- 用户批准或拒绝操作后，任务能继续、暂停或安全结束。
- 同一任务可查看完整文件操作时间线。

## F4：文档质量检查模式

**用户价值：** 用户可以用同一平台生成符合既定规范的 README、技术文档和报告。

### 功能内容

1. 提供文档任务模板：README、技术设计、周报、复盘报告。
2. 提供可选择的规则：必填标题、标题层级、字数区间、链接格式、关键词、禁止占位文本。
3. Generator 生成文档后，规则检查器输出可定位的问题；Critic 负责给出可读性、逻辑性等建议。
4. 在最终结果中分别展示“规则通过情况”和“模型审查建议”，避免混淆客观检查与主观评价。
5. 支持粘贴初始草稿并迭代润色。

### 主要影响范围

- 新增 `backend/src/verification/document_verifier.py`
- `backend/src/prompts/`
- `backend/src/models/`
- 工作台或文档任务专用页面

### 验收标准

- 一个缺失必填章节的文档会被规则检查阻止完成，并在下一轮得到明确反馈。
- 用户可以选择模板并查看每条规则的通过/失败原因。
- 可导出最终 Markdown 与审查记录。

## F5：方案生成与计划校验模式

**用户价值：** 用户可以生成结构完整、可执行的 PRD 或技术方案，而不是只获得一段散文。

### 功能内容

1. 提供 PRD、技术方案和项目计划模板。
2. 对结构化 JSON 输出执行 Schema 校验；对 Markdown 方案执行必填章节校验。
3. 支持把任务计划转换为子任务依赖图，检查缺失依赖与循环依赖。
4. 允许用户在迭代前锁定关键约束，例如预算、技术栈、非功能需求和交付时间。
5. 导出 Markdown、JSON 和任务清单。

### 主要影响范围

- 新增 `backend/src/verification/plan_verifier.py`
- `backend/src/planner/task_planner.py`
- `backend/src/models/task.py`
- 新增方案模板与依赖图前端组件

### 验收标准

- 缺少关键章节、存在循环依赖的方案不能获得“规则通过”。
- 用户可从方案页查看子任务图并导出计划。
- 生成的计划可直接创建为长任务，不需要手工复制粘贴。

## F6：运行历史、对比与复用

**用户价值：** 用户能理解 Agent 的质量、成本和迭代过程，并复用有效配置。

### 功能内容

1. 保存每次运行的模型、提示词版本、阈值、预算、验证器、轮次和结果摘要。
2. 提供运行历史列表与筛选：任务类型、状态、是否验证通过、时间区间。
3. 支持比较两次运行的评分、验证结果、Token、耗时和文件变更。
4. 支持将某次任务保存为模板，复用其模式、规则和运行配置。
5. 提供 JSON/Markdown 导出。

### 主要影响范围

- `backend/src/store/state_store.py`
- `backend/src/models/`
- `backend/routers/tasks.py`
- 新增历史与对比页面

### 验收标准

- 已完成任务可重新打开并查看关键运行参数与每轮记录。
- 用户可选择两次运行并看到差异。
- 模板可创建新任务，但不复用旧任务的运行状态或工作区写入权限。

## F7：评估中心与基准报告

**用户价值：** 项目能用数据展示“验证驱动迭代”的收益与成本，也能帮助用户选择运行策略。

### 功能内容

1. 将现有 `benchmark/` 封装为可管理的基准任务集。
2. 提供策略组合：单次生成、Generator-Critic、Generator-Critic + 验证器。
3. 记录任务通过率、平均轮数、平均 Token、平均耗时、失败类型。
4. 提供报告页面与 Markdown/CSV 导出。
5. 为基准运行加上模型、提示词版本、日期和随机性说明，避免误读结果。

### 主要影响范围

- `benchmark/`
- `backend/routers/`（新增 benchmark 路由）
- 新增 benchmark 前端页面与图表

### 验收标准

- 至少有代码和文档两类固定任务集。
- 同一策略可重复运行，原始结果可导出。
- 报告同时呈现成功率收益和成本，不只展示最有利指标。

## 5. 功能发布顺序

| 版本 | 包含功能 | 对用户的可见变化 |
|---|---|---|
| v0.2 | F1 + F2 | 用户能创建带验证命令的代码任务，并看到自动修复与测试证据 |
| v0.3 | F3 + F4 | 用户可确认文件变更，并可完成规则驱动的文档任务 |

## 6. 功能优先级原则

开发中按以下顺序做取舍：

1. **证据优先：** 能产生测试、规则检查或结构校验证据的功能优先于纯模型评分功能。
2. **闭环优先：** 优先完成“创建 → 执行 → 查看证据 → 决策”的完整用户流程，不做孤立页面。
3. **共享内核优先：** 代码、文档、方案应复用编排、任务、记录与展示模型；只在验证器和模板层区分。
4. **人工可控：** 涉及真实文件写入、删除和最终交付的功能必须支持用户停止或确认。
5. **可度量：** 每个新增模式至少有一个确定性验收规则和一个可复现示例。

## 8. 第一阶段建议

第一阶段只实现 **F1 + F2**。完成后，用户就能选择“代码任务”，配置工作区与测试命令，看到 Agent 修复代码并以真实验证结果决定是否完成。这是目前最完整、最有差异化、也最适合作为主 Demo 的功能闭环。
